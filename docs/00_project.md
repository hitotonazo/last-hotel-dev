# 1. 最重要ルール

1.  作品名は**必ず `HOTEL NESTRA`**。旧名称 `THE LAST HOTEL`
    を画面、コード内表示文言、README、共有文等に残さない。
2.  PHASE0は「実在しそうな高級都市型ホテル公式サイト」として完成させる。ARGを優先して通常サイトを簡素化しない。
3.  プレイ時間は20〜60分、進行は一本道。
4.  各PHASEで新しく発見する主要異常は原則1箇所。
5.  異常クリックでPHASEが進む場合、プロジェクト内 `modules`
    の**サイト改変演出を必ず再生**する。
6.  同じ異常でサイト改変演出を再生するのは初回のみ。再訪・reload・history
    backで重複再生しない。
7.  `modules` の**デバッグ機能を必ず流用**し、URLに `?debug=1`
    を付けるとデバッグUIが出現すること。
8.  `modules` と同等の改変演出・debug機能を新規実装し直さない。
9.  `modules`
    のAPI、class、data属性、保存方式、表示タイミング等を実装前に確認する。仕様変更が必要なら勝手に改修せず理由と影響範囲を報告する。
10. 重要ストーリー情報は日本語で理解できるようにする。英語はブランド、ラベル、補助表記に留める。
11. AI生成画像内の文字を正式情報として読ませない。重要文言・数値・資料本文はHTMLで実装する。
12. PC/SPの双方で攻略可能にする。hoverのみを攻略条件にしない。
13. 仕様書にないページ追加、ページ統合、タブ化、モーダル連続化、分岐追加を禁止する。
14. 仕様書にないホラー演出、ジャンプスケア、流血、過剰なグリッチ、SF的な未来UIを追加しない。
15. 真相ページの不気味さは「意味不明」ではなく「内容を理解した結果として不気味」にする。

# 4. デザイン方向性

## 4-1. 通常サイト

参考デザインの「ブラック／深いグリーン／暗いグラデーションを使った高級感」を視覚基準にする。ただし参考サイトのレイアウト自体は踏襲しない。

推奨方向：

-   ベース：ブラック、チャコール、ダークブラウン、深いグリーン
-   明るいセクションを適度に混ぜ、全ページを真っ黒にしない
-   グラデーションは背景の奥行きとして控えめに使用
-   写真を大きく使う
-   細い罫線、十分な余白、上品なタイポグラフィ
-   ホテルサイトとして自然なフェード・hover

禁止：

-   最初から赤をブランドカラーとして多用する
-   通常サイトでノイズ・警告・ターミナルUIを見せる
-   ARGらしい不穏さをPHASE0から出す
-   参考サイトのセクション順・レイアウトをコピーする

## 4-2. 赤色の役割

赤は通常ブランド色ではなく、ARGで露出した異常・増設情報・031の識別に限定する。

-   031の真っ赤な服
-   `floor-map-hidden.png` の10F
-   `facility-extension-plan.png` の増設部分/B2
-   内部資料の警告・重要状態の限定的な強調

# 4-3. フォント指定

HOTEL
NESTRAでは、以下の3書体を正式フォントとして使用する。CodeX判断で別書体へ置換しない。

  用途           使用フォント
  -------------- ----------------------
  日本語見出し   `Shippori Mincho`
  英語           `Cormorant Garamond`
  日本語本文     `Noto Sans Japanese`

適用ルール：

-   日本語のページタイトル、セクション見出し、主要コピー：`Shippori Mincho`
-   `HOTEL NESTRA`、英語見出し、英語ラベル、英数字を主体とする装飾見出し：`Cormorant Garamond`
-   日本語本文、ナビゲーション、ボタン、注釈、館内情報、内部資料本文：`Noto Sans Japanese`
-   日本語と英語が混在する見出しは、要素またはspanを分けて上記ルールを適用してよい。
-   フォント読み込み元が提供する正式な `font-family`
    名を確認して実装する。指定書体を類似フォントへ勝手に変更しない。
-   読み込み失敗時に備え、適切なserif / sans-serif fallbackを設定する。
-   font-weightは実際に読み込んだweightのみを使用し、ブラウザの擬似boldへ過度に依存しない。
-   PHASE進行後も基本フォント体系は維持する。異常演出のために全面的に別フォントへ切り替えない。

推奨CSS変数例：

``` scss
:root {
  --font-heading-ja: "Shippori Mincho", serif;
  --font-en: "Cormorant Garamond", serif;
  --font-body-ja: "Noto Sans Japanese", sans-serif;
}
```

# 10. SCSS / CSS

原則SCSSを正とする。

推奨：

``` text
assets/
  scss/
    style.scss
    foundation/
    layout/
    component/
    project/
    utility/
  css/
    style.css
```

-   SCSS entry pointは原則 `assets/scss/style.scss` 1つ
-   HTMLは基本 `assets/css/style.css` のみを読み込む
-   `style.css` を直接編集しない
-   `package.json` に `build` / `watch` を用意
-   SCSS変更後はCodeX自身がbuildを実行
-   納品時にSCSSだけ更新されCSS未反映という状態を禁止
-   READMEに編集元、buildコマンド、CSS出力先を記載

# 11. JavaScript / 状態管理

状態はlocalStorageを基本とする。

推奨する単一state：

``` js
{
  phase: 'phase0',
  discovered031: false,
  discovered10F: false,
  discoveredRenovation: false,
  discoveredB2: false,
  undergroundViewed: false,
  truthReached: false,
  endingTriggered: false
}
```

キー名はプロジェクト内で1つに統一する。既存modules側に状態管理契約がある場合はそちらを優先し、二重管理しない。

必須：

-   reload後も現在状態を再描画
-   ページ移動後も状態維持
-   history backで破綻しない
-   JSON parse失敗時は安全に初期化
-   不正phaseはphase0相当へフォールバック
-   連打でPHASEが複数進行しない
-   演出中は対象操作を一時ロック

# 12. modules

プロジェクト内 `modules` を必ず先に調査する。

必須流用：

1.  サイト改変演出
2.  デバッグ機能

サイト改変演出：

-   新しい主要異常を初めて発見しPHASEが進む時に1回
-   異常箇所クリック後、確実に再生
-   演出完了後にUI差し替えまたは次ページ遷移
-   発見済み異常の再クリックでは再生しない

デバッグ：

-   `?debug=1` で必ず出現
-   本番通常URLでは出現しない
-   phase切替
-   発見済み状態確認/切替
-   改変演出テスト
-   reset
-   現在state確認

modulesに既存UI・ショートカットがある場合はそれを優先する。

# 16. CodeX実装手順

一括実装しない。

### STEP 1｜共通基盤

実装：ファイル構造、Header、Footer、container、font、SCSS
build、responsive基盤、modules確認、探索リセットUI。

このSTEPではゲーム本実装を完成させなくてよい。

終了時に報告：

-   変更ファイル
-   SCSS entry / build command / output CSS
-   modulesの確認結果
-   PC/SP Header/Footer確認
-   未実装項目

承認までSTEP2へ進まない。

### STEP 2｜PHASE0通常サイト

`index.html`、`facilities.html`通常状態、`gallery.html`通常状態を完成。

終了条件：普通の高級ホテルとしてPC/SPとも成立。ARG情報を先出ししない。

### STEP 3｜ARG前半

PHASE1〜PHASE3を実装。

`031 → 10F → 2021年増設EV → 改装記録 → B2増設区画`

各初回異常でmodules演出が確実に1回だけ再生されること。

### STEP 4｜地下・真相・締め

`underground.html`、`truth.html`、空室3→4、031消失、X共有まで実装。

### STEP 5｜ゲームロジック統合・最終検証

state、直接アクセス、reload、back、再訪、reset、`?debug=1`、SP、reduced
motion等を通し確認。

# 17. 各STEP共通の終了報告

CodeXは各STEP終了時に必ず以下を報告する。

1.  実装した内容
2.  変更したファイル
3.  仕様書から変更した点の有無
4.  PC/SP確認結果
5.  build結果
6.  PHASE/state確認結果（該当STEPのみ）
7.  未実装項目

勝手に次STEPへ進まない。
